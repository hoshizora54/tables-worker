# Агент для анализа данных с Tool Use

Система интерактивного анализа табличных данных (CSV/XLSX) на естественном языке с использованием агентской архитектуры и Tool Use. Агент автоматически выбирает и применяет инструменты для выполнения запросов пользователя.

## Основные возможности

- **Агентская система с Tool Use**: LLM самостоятельно выбирает и вызывает инструменты на основе запросов на естественном языке
- **Загрузка данных**: CSV/XLSX → SQL (SQLite по умолчанию, PostgreSQL опционально)
- **Интерактивный анализ**: Единое поле ввода для запросов на естественном языке
- **Статистический анализ**: t-тесты, ANOVA, скользящие средние, группировки, сводные таблицы
- **Визуализация**: Автоматическое построение графиков (гистограммы, столбчатые, линейные, scatter)
- **Версионирование**: Откат состояний таблиц и экспорт версий
- **Безопасность**: Ограничение на опасные SQL-операции
- **Понятные ответы**: Финальный ответ — развернутый и человеко‑понятный (итог, смысл, ключевые цифры, рекомендации)

## Архитектура

### Backend (FastAPI)

- **Агентский сервис** (`backend/services/agent_service.py`): Реализует агентский цикл с выбором инструментов
- **Сервис инструментов** (`backend/services/tool_service.py`): Определяет доступные инструменты и их выполнение
- **LLM сервис** (`backend/services/llm_service.py`): Интеграция с YandexGPT для генерации SQL и ответов
- **API эндпоинты**:
  - `/api/v1/llm/agent` — **основной эндпоинт** для агентских запросов
  - `/api/v1/ingest/*` — загрузка файлов
  - `/api/v1/schema/*` — работа со схемой БД
  - `/api/v1/query/*` — прямые SQL-запросы
  - `/api/v1/versioning/*` — версионирование

### Frontend (Vue.js)

- Упрощенный интерфейс с единым полем ввода на естественном языке
- Автоматическое отображение результатов: таблицы, графики, статистика
- Управление таблицами и версиями

### Инструменты (Tools)

Агент имеет доступ к следующим инструментам:

1. **sql_query** — выполнение SQL SELECT запросов
2. **t_test** — t-тест для сравнения двух групп
3. **anova** — однофакторный ANOVA
4. **moving_average** — скользящее среднее
5. **groupby** — группировка с агрегацией
6. **pivot** — сводные таблицы
7. **join** — объединение таблиц
8. **plot** — построение графиков (bar, line, hist, scatter)
9. **filter** — фильтрация данных

```env
# DATABASE_URL=postgresql://user:pass@host:port/db

# Yandex GPT

YANDEX_API_KEY=ваш_api_key
YANDEX_FOLDER_ID=ваш_folder_id
YANDEX_LLM_MODEL=yandexgpt-lite
YANDEX_COMPLETION_URL=https://llm.api.cloud.yandex.net/foundationModels/v1/completion

# CORS
CORS_ORIGINS=*

```

### Переменные окружения и режимы

- `LLM_ONLY_SQL=0|1` — режим работы агента:
  - `0` (по умолчанию): доступны все инструменты (sql_query, t_test, anova, plot, groupby и т.д.)
  - `1`: агент использует только инструмент `sql_query` (все шаги анализа делаются SQL‑запросами)

## Использование

### Основной сценарий: Агентский запрос

1. Загрузите CSV/XLSX файл через интерфейс
2. Введите запрос на естественном языке в единое поле ввода, например:
   - "Построй гистограмму распределения возраста"
   - "Сравни продажи в группах А и Б с помощью t-теста"
   - "Посчитай средние продажи по категориям"
   - "Создай сводную таблицу по регионам и продуктам"
   - "Вычисли скользящее среднее продаж за последние 7 дней"

3. Агент автоматически:
   - Проанализирует запрос
   - Выберет подходящие инструменты
   - Вызовет их с правильными параметрами
   - Вернет результаты (таблицы, графики, статистику)

### Примеры запросов

**Статистический анализ:**
- "Сравни средние значения в группах 'контроль' и 'эксперимент' по колонке 'результат'"
- "Выполни ANOVA для сравнения продаж по регионам"

**Визуализация:**
- "Построй гистограмму распределения возраста"
- "Создай столбчатую диаграмму продаж по категориям"
- "Покажи линейный график тренда продаж по месяцам"

**Аналитика:**
- "Посчитай средние продажи по категориям"
- "Создай сводную таблицу: строки — регионы, столбцы — продукты, значения — сумма продаж"
- "Вычисли скользящее среднее продаж с окном 7 дней"

**Работа с данными:**
- "Покажи первые 100 строк из таблицы"
- "Отфильтруй данные где возраст больше 30"
- "Объедини таблицы users и orders по user_id"

### Как формируется финальный ответ

Финальный ответ теперь всегда развернутый и структурированный:
- Короткий итог — одна фраза с главным выводом
- Что это значит — 1–2 предложения человеческим языком
- Ключевые цифры — списком (например, топ‑N, минимум/максимум, среднее, сравнение показателей)
- Рекомендации — 1 практический шаг
- Ограничения — если данных мало/неполны

### Что было сделано в рамках задачи (улучшения)

- Наладил генерацию SQL под SQLite:
  - Жесткие правила кавычек для таблиц и колонок (всегда "...")
  - Запрет функций других СУБД (DATE_FORMAT, DATE_TRUNC, EXTRACT, TO_CHAR)
  - Паттерны для группировки по месяцам: `strftime('%Y-%m', "Дата")` или `substr(...)` для dd.mm.YYYY
  - Нормализация чисел с пробелами/запятыми при вычислениях: `CAST(REPLACE(REPLACE("Колонка", ' ', ''), ',', '.') AS FLOAT)`
  - В промпт добавлены примеры строк таблиц (row_samples), чтобы LLM видела реальные имена и значения
  - Передача `table_hint` для повышения точности выбора таблицы
- Улучшил агентную систему:
  - Четкие инструкции выбора инструментов и перехода от `sql_query` к аналитике (`t_test`, `anova`, `plot`, `groupby`)
  - Режим `LLM_ONLY_SQL`: строго разрешает только `sql_query`, аналитика выполняется последовательностью SQL
  - Предотвращение повторения одного и того же SELECT и подсказки LLM перейти к следующему шагу
  - Подробная обратная связь при ошибках SQL (правила для SQLite + перечень допустимых колонок таблицы)
  - Ошибки логируются, но не попадают в UI; в UI возвращаются содержательные результаты
- Отнормировал итоговый вывод LLM:
  - Строгая структура ответа: Итог → Смысл → Ключевые цифры → Рекомендации → Ограничения
  - Детерминированная сводка для табличных результатов (без риска неверных чисел от LLM): топ‑N категорий, минимум/максимум и среднее; для чисто числовых колонок — среднее, медиана, квартиль Q1/Q3, минимум/максимум, стандартное отклонение, сравнение первых двух метрик (средняя разница, доля строк A>B, корреляция r)
  - Корректный парсинг чисел со строковыми форматами (запятые/пробелы/%) для точной статистики

## Как работает агентская система

1. **Пользовательский запрос** поступает в агентский сервис
2. **Агент анализирует запрос** с помощью LLM, получая:
   - Описание схемы БД (таблицы, колонки, типы)
   - Список доступных инструментов с описаниями
3. **LLM выбирает инструмент** и формирует JSON с параметрами
4. **Инструмент выполняется** на бэкенде
5. **Результат возвращается** агенту
6. **Агент может выполнить несколько итераций** для сложных запросов
7. **Финальный ответ** формируется на основе всех результатов

## API

### Основной эндпоинт: Агентский запрос

```http
POST /api/v1/llm/agent
Content-Type: application/json

{
  "task": "Построй гистограмму распределения возраста",
  "table_hint": "users"  // опционально
}
```

Ответ:
```json
{
  "tool_calls": [
    {
      "tool_name": "plot",
      "parameters": {...}
    }
  ],
  "results": [
    {
      "tool_name": "plot",
      "parameters": {...},
      "result": {
        "image_base64": "...",
        "rows": [...],
        "type": "hist"
      }
    }
  ],
  "final_answer": "Короткий итог: распределение возраста построено, виден основной диапазон значений.\nЧто это значит: большинство объектов сосредоточены вокруг центральных значений; хвосты указывают на редкие наблюдения.\nКлючевые цифры:\n- Среднее: 35.20; медиана: 34.00; мин: 18.00; макс: 72.00\nРекомендации: при необходимости сегментируйте по категориям (например, полу или региону) и сравните распределения."
}
```

### Другие эндпоинты

- `POST /api/v1/ingest/upload` — загрузка файлов
- `GET /api/v1/schema/tables` — список таблиц
- `GET /api/v1/schema/tables/{table}/sample` — превью таблицы
- `POST /api/v1/query/sql` — прямой SQL-запрос (только SELECT/WITH)
- `GET /api/v1/versioning/versions/{table}` — история версий
- `POST /api/v1/versioning/versions/{table}/restore/{version}` — откат версии

## Отличия от предыдущей версии

### Что изменилось

1. **Агентская архитектура**: Вместо детерминированных API-эндпоинтов создана система Tool Use, где LLM самостоятельно выбирает инструменты
2. **Упрощенный UI**: Убраны ручные селекторы для графиков и аналитики, оставлено единое поле ввода
3. **Автоматический выбор инструментов**: Агент сам определяет, какой инструмент использовать для каждого запроса
4. **Итеративный цикл**: Агент может выполнять несколько шагов для сложных запросов
5. **Развернутые ответы**: Финальный ответ стал подробнее и понятнее (итог, смысл, ключевые цифры, рекомендации)
6. **Режим LLM_ONLY_SQL**: Опционально можно ограничить агента только SQL‑запросами (ENV `LLM_ONLY_SQL=1`)

### Что осталось

- Загрузка файлов и работа с таблицами
- Версионирование и откат состояний
- Экспорт данных
- Безопасность SQL (только SELECT/WITH и безопасные write-операции)

## Безопасность

- Разрешены только SELECT/WITH запросы через прямой SQL
- Безопасные write-операции: `ALTER TABLE ... RENAME COLUMN` и `UPDATE ... WHERE ...`
- Все инструменты проверяют входные данные
- SQL-инъекции предотвращаются через параметризованные запросы

## Разработка

### Добавление нового инструмента

1. Добавьте определение в `backend/services/tool_service.py`:
   - Добавьте `ToolDefinition` в `get_tools_definitions()`
   - Реализуйте вызов в `call_tool()`

2. Инструмент автоматически станет доступен агенту

## Бенчмаркинг

Система поддерживает оценку производительности через бенчмарки с Hugging Face.

### Установка зависимостей для бенчмарка

```bash
pip install datasets
```

### Запуск бенчмарка

```bash
# Убедитесь, что бэкенд запущен
uvicorn backend.main:app --host 127.0.0.1 --port 8000

# В другом терминале запустите бенчмарк
python scripts/run_benchmark.py --dataset sql-create-context --limit 20
```

### Доступные бенчмарки

- **sql-create-context** (рекомендуется) - `b-mc2/sql-create-context`
- **spider** - Text-to-SQL бенчмарк
- **wikisql** - WikiSQL бенчмарк

### Метрики

Бенчмарк вычисляет:
- **Execution Accuracy** - точность выполнения запросов
- **SQL Usage Rate** - доля использования SQL инструмента
- **Среднее время выполнения** - производительность системы

Подробнее см. `scripts/README_BENCHMARK.md`
